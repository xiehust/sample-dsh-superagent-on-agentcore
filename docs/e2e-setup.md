# E2E setup checklist (A2): GitHub App + Feishu/Lark bot

Follow this once, after `scripts/deploy.sh` has deployed every `dshsa-*` stack in ap-northeast-1. Onboarding happens in the panel. The only command-line steps are reading the deployment outputs, creating the first platform admin, and copying the webhook secret. At the end, A2 runs end to end: mention → acknowledgement → PR → ready reply, both from GitHub and from a bound Feishu chat.

Commands run from the repository root with the platform admin's AWS credentials for the account in `DSHSA_ACCOUNT` (exported, or set in the untracked `scripts/local.env`). `dshsa-admin` is run as `pnpm --filter @dshsa/control-api admin <command>`, abbreviated `admin` below:

```sh
export AWS_REGION=ap-northeast-1
alias admin='pnpm --silent --filter @dshsa/control-api admin'
```

Keep secrets (the App private key, the OAuth client secret, the Feishu App Secret) out of chat, tickets and this repository. The panel's secret fields are write-only: they never show a stored value.

The command blocks in this guide contain no `#` comments, so they paste safely into zsh, where interactive comments are off by default.

## 0. Collect the deployment outputs

Show the stack outputs and check the ingress. `check:ingress` must print ✓ on every line before you continue:

```sh
aws cloudformation describe-stacks --stack-name dshsa-ingress --query "Stacks[0].Outputs" --output table
aws cloudformation describe-stacks --stack-name dshsa-panel --query "Stacks[0].Outputs" --output table
pnpm --filter @dshsa/sources check:ingress
```

- **Webhook URL**: output `GithubWebhookUrl` of `dshsa-ingress`. Re-read it if the stack is ever destroyed and redeployed, because the API id changes.
- **Panel URL**: output `PanelUrl` of `dshsa-panel`, written `<PanelUrl>` below (`https://<distribution>.cloudfront.net`, no trailing slash).
- **Webhook secret**: the `webhookSecret` in `dshsa/github-app`, generated by `dshsa-shared`. **It is sensitive**: anyone holding it can sign webhook deliveries that the ingress accepts. Don't print it, and paste it nowhere except the App's **Webhook secret** field in step 1. Copy it straight to the clipboard right before that step, without showing it.

  On macOS:

  ```sh
  aws secretsmanager get-secret-value --secret-id dshsa/github-app --query SecretString --output text | jq -r .webhookSecret | tr -d '\n' | pbcopy
  ```

  On a Linux desktop, replace `pbcopy` with `wl-copy` (Wayland) or `xclip -selection clipboard` (X11). In a shell on a remote host over SSH, such as a dev desktop, send it to your local clipboard with an OSC 52 escape sequence instead. The terminal consumes the sequence and doesn't display it. Your terminal must allow clipboard access (iTerm2: *Applications in terminal may access clipboard*; inside tmux: `set -g set-clipboard on`):

  ```sh
  printf '\033]52;c;%s\a' "$(aws secretsmanager get-secret-value --secret-id dshsa/github-app --query SecretString --output text | jq -r .webhookSecret | tr -d '\n' | base64 | tr -d '\n')"
  ```

  After pasting it into the App, copy something else to clear the clipboard.

## 1. Create the GitHub App (platform, once)

GitHub → **Settings → Developer settings → GitHub Apps → New GitHub App** (or under the organization that should own the App: **Organization settings → Developer settings → GitHub Apps**). [github-app.md](github-app.md) explains each setting.

- [ ] **GitHub App name**: a short name, for example `dshsa-e2e-agent`. Its **slug** (shown on the App page after creation) is what people mention: `@dshsa-e2e-agent`.
- [ ] **Homepage URL**: any URL, for example `<PanelUrl>`.
- [ ] **Identifying and authorizing users**: click **Add redirect URI** and enter the **Redirect URI** (formerly Callback URL) `<PanelUrl>/setup/github/callback`. Leave **Allow wildcard matching** and **Request user authorization (OAuth) during installation** unchecked, and leave **Enable Device Flow** off.
- [ ] **Post installation → Setup URL**: `<PanelUrl>/setup/github`, and turn on **Redirect on update**. GitHub then returns people to the panel after they install the App or change its repositories.
- [ ] **Webhook → Active**: on.
- [ ] **Webhook URL**: `https://<api-id>.execute-api.ap-northeast-1.amazonaws.com/github/webhook` (the `GithubWebhookUrl` from step 0).
- [ ] **Webhook secret**: paste the `webhookSecret` you copied to the clipboard in step 0.
- [ ] **SSL verification**: enabled.
- [ ] **Repository permissions**:

  | Permission | Access |
  |---|---|
  | Actions | Read-only |
  | Checks | Read-only |
  | Commit statuses | Read-only |
  | Contents | Read and write |
  | Issues | Read and write |
  | Metadata | Read-only (mandatory) |
  | Pull requests | Read and write |

- [ ] **Organization permissions → Members**: Read-only. The panel uses it to check that whoever links an organization's installation is an admin of that organization. Every other repository, organization and account permission: **No access**.
- [ ] **Subscribe to events**: `Check suite`, `Issue comment`, `Issues`, `Pull request`, `Pull request review`, `Pull request review comment`, `Status`, `Workflow run`.
- [ ] **Where can this GitHub App be installed?**: "Only on this account", or "Any account" if a team's repositories live in another account or organization.
- [ ] **Create GitHub App**, then note the **App ID** (numeric) and the **Client ID** (`Iv…`).
- [ ] **Client secrets → Generate a new client secret**. GitHub shows it once; keep it for step 3.
- [ ] **Private keys → Generate a private key**: save the `.pem` outside the repository, for example `~/dshsa-e2e-agent.private-key.pem`.
- [ ] Advanced → **Recent Deliveries** shows the `ping` with **200**. This already works, because `dshsa-shared` generated the webhook secret. A **401 bad_signature** means the App's webhook secret differs from `webhookSecret`. Copy it again (step 0), paste it, and **Redeliver**.

Don't install the App yet; the team admin does that from the panel in step 5.

## 2. Create the first platform admin (CLI, once)

This is the one onboarding step that stays on the command line: every later admin is invited in the panel. Cognito emails a temporary password, and the first sign-in asks for a new one. If no email arrives, add `--temp-password '<Temp-Passw0rd!>'` and sign in with that.

```sh
admin user add-admin <admin-email>
```

## 3. Platform setup in the panel

Open `<PanelUrl>` and sign in as the platform admin. The **Platform** tab has four sections: **Teams**, **Users**, **GitHub App** and **GitHub installations**.

**GitHub App.** The section repeats the step 1 checklist under **On GitHub (App settings → General)**, with copy buttons for the Redirect URI and the Setup URL. Fill in the form and press **Save GitHub App**:

- [ ] **App ID**: the numeric App ID.
- [ ] **Private key (.pem)**: paste it, or pick the file under **Upload private key**. The key stays in the page until you save.
- [ ] **Client ID** and **Client secret**: from step 1.
- [ ] Leave **Webhook secret (optional)** empty. It is only for changing the secret, and needs the private key in the same save.

The panel checks the App ID and key with GitHub and reads the App's slug from GitHub; there is nothing to type for it. Afterwards the section shows **App ID … · slug …**, **Private key: Valid** and **OAuth client: Set · Client ID …**. Running hosts pick up a new key within 5 minutes; there is no restart.

**Teams.** Under **Create team**, enter a **Team id** (3–31 lowercase letters, digits or hyphens, starting with a letter; `admin`, `tadmin` and `platform` are reserved), for example `e2ea`, and a **Name**, then press **Create team**.

**Users.** In **Users of**, pick the new team. Under **Invite user to <team>**, enter the **Email** of its first team admin, choose **Role: Team admin**, and press **Invite**. Cognito emails them a temporary password. With **Users of: Platform admins**, the same form invites more platform admins.

A platform admin can also do the team setup below for any team: with more than one team, pick it in the header's **Team** selector.

## 4. Team setup: checklist

Sign in as the team admin (or stay signed in as the platform admin) and open **Team setup**. The **Onboarding checklist** at the top tracks the steps below, each with a link to its section:

1. GitHub App installed and linked to this team
2. A repository added
3. Feishu / Lark bot connected
4. A chat bound to a repository
5. People allowed to start work (**Open the Policy form**; this one is per repository, so it isn't ticked)

The sections are **Repositories**, **Feishu / Lark**, **Chats** and **Users**.

## 5. Team setup: Repositories

- [ ] **Install / configure the GitHub App** opens GitHub's install page in a new tab. Pick the account or organization that owns the test repository, choose **Only select repositories**, and pick it (A1). GitHub then returns to `<PanelUrl>/setup/github`, which says **GitHub App installed**; press **Go to Repositories**.
- [ ] **Link installations**. GitHub asks you to sign in and authorize the App, so the panel can check which installations your GitHub account can access. It then shows **Linking GitHub installations** with one line per installation:
  - **Linked to your team**: the installation is on your own GitHub account, or on an organization where you are an **admin**. It is active right away.
  - **Waiting for platform approval**: anyone else, for example an organization member who isn't an admin. The reason is shown next to it. A platform admin approves it under **Platform → GitHub installations → Approve** (or **Reject**). Someone who controls the account on GitHub (its owner or an organization admin) can also link it themselves instead.
  - **Belongs to another team**: another team has already linked it. A platform admin can release it under **Platform → GitHub installations**.

  Press **Continue to Repositories**.
- [ ] Under **Linked installations**, an active installation lists the repositories it can access. Press **Add** on the test repository. The panel says **Added <owner>/<repo>. Its cell starts within a minute.** It appears under **Repositories of this team**, where **Pause**, **Enable** and **Disable** change its status. The cell id is `<teamId>--gh<repoId>`; nothing is typed by hand.
- [ ] Nothing is listed? The installation has no access to that repository: press **Install / configure the GitHub App** again and add it. **Redirect on update** brings you back.

**Unlink** removes the team's link to an installation, so another team can link it; the App stays installed on GitHub. It is refused while a repository of this team still uses the installation: **Disable** those repositories first. A platform admin's **Release** under **Platform → GitHub installations** has a **Release anyway** option, which leaves those repositories as they are.

## 6. Team setup: Feishu / Lark

One self-built app per team: the platform keeps one long connection per app, and Feishu delivers each event of an app to only one connection. Open the developer console of the platform the test chat lives on: Feishu https://open.feishu.cn/app or Lark https://open.larksuite.com/app. The panel's **Feishu / Lark console checklist** lists the same steps. [feishu-bot.md](feishu-bot.md) has the details.

- [ ] **Create custom app** (创建企业自建应用): any name, for example `dshsa e2e agent`.
- [ ] **Add features → Bot** (添加应用能力 → 机器人).
- [ ] **Permissions & scopes** (权限管理). Grant these tenant-token scopes, search by the console name:
  - [ ] Receive group chat messages that @ the bot (接收群聊中@机器人消息事件)
  - [ ] Read direct messages sent to the bot (读取用户发给机器人的单聊消息)
  - [ ] Obtain and send messages in direct and group chats (获取与发送单聊、群组消息)
  - [ ] Obtain group information (获取群组信息)
  - [ ] Obtain group members (获取群成员信息)
  - [ ] Read and upload images or files (获取与上传图片或文件资源)
  - [ ] Optional: Read all messages in groups (获取群组中所有消息), only for a chat set to **All** instead of **@ only**
- [ ] **Credentials & basic info** (凭证与基础信息): copy the **App ID** (`cli_…`) and **App Secret** into the panel's **Feishu / Lark bot** form: **Platform** (Feishu or Lark), **App ID**, **App Secret**, and **Encrypt Key (optional)** only if you set one under Events & callbacks. Press **Save bot**. The App Secret is needed again on every save.
- [ ] Wait until the form shows **Connected** with **Listening for bot events** (within about a minute). **Starting** means the Connector is connecting; **Error** shows the cause.
- [ ] **Events & callbacks → Event configuration** (事件与回调 → 事件配置): subscription mode **Receive events through persistent connection** (使用长连接接收事件), then save. The console accepts it only while the Connector is connected. Add the event **Message received** `im.message.receive_v1` (接收消息).
- [ ] **Version management & release** (版本管理与发布): create a version and publish it. Have the Feishu tenant admin approve it in the admin console if asked.

## 7. Team setup: Chats

- [ ] Add the bot to the test chat (chat settings → **Bots → Add bot**) and send one message that @-mentions it. The chat shows up under **Chats** within a minute, with **1 message waiting for a binding**. The bot must be in the group: a chat the bot has never seen is not listed.
- [ ] In the chat's **Repository** column, pick the test repository from **Choose a repository…**. The binding reaches the cell within a minute, as **@ only**. **Unbind** removes it.
- [ ] **Settings → Feishu chat bindings** (per repository) lists the bound chat.

## 8. Team setup: Users

Invite the team's other people here: **Email**, **Role** (**Member** or **Team admin**), **Invite**. Members read everything and may Stop or Retry tickets. Team admins also change settings, repositories, the bot and chats.

## 9. Settings → Policy

Pick the repository in the header's cell selector, open **Settings**, and go to **Policy**. It has two tabs, **Form** and **Advanced (JSON)**. Members see both read-only.

**Form:**

- [ ] **Eval mode**: **Off**, **Observe** (the default) or **Auto**, saved with **Save Eval mode**. It only affects messages that don't @-mention the agent and aren't direct messages. An @-mention from someone on the list is evaluated in every mode, so A2 needs no change here.
- [ ] **GitHub → GitHub accounts that may originate work**: press **Add from repo collaborators** and **Add** yourself (or **Add all**), or use **Add row** and type the login without `@`.
- [ ] **Feishu → Feishu users who may originate work**: press **Add all members of <chat>**, or **Pick from <chat>** and **Add** yourself. The rows hold each person's `open_id` for this bot and their name. The buttons list only chats bound to this repository.
- [ ] Press **Save** in the **Unsaved changes** bar. If someone else saved in the meantime, the save is refused: **Reload** and reapply your edit. The cell checks the Policy and shows its errors next to the field.

**Sync chat** (under Feishu) is optional: with a chat chosen there, the list becomes that chat's members at startup and on **Sync now**. **Advanced (JSON)** edits the whole `{ "rules": [...], "sources": {...} }` block, including the rules the form doesn't show.

## 10. Run A2

- [ ] **GitHub**: in the test repository, open an Issue and comment `@<app-slug> add a CONTRIBUTING.md with a short how-to-build section`. Expect, in order: a webhook delivery with **202** in **Recent Deliveries**, an acknowledgement comment by `<app-slug>[bot]`, a PR from an `agent/<name>` branch by `<app-slug>[bot]`, then a ready reply in the Issue. The panel's Overview shows the ticket.
- [ ] **Feishu**: in the bound chat, send `@<bot name> add a short FAQ section to README.md`. Expect a threaded acknowledgement from the bot, a PR in the bound repository, then a ready reply in the same thread.
- [ ] Automated checks: `scripts/e2e/run.sh` (A5, A6 and the ingress checks) must print `all steps passed`.

## Troubleshooting

Host logs are in the CloudWatch log group `/dshsa/host`. The panel's setup actions are audited in `/dshsa/panel-admin`, and panel-api logs to `/dshsa/panel-api`.

| Symptom | Where to look / fix |
|---|---|
| Recent Deliveries shows 401 | The App's webhook secret differs from `dshsa/github-app` `webhookSecret`. Copy it again (step 0) and paste it |
| Recent Deliveries shows 503 | The Lambda cannot read a usable `webhookSecret` (missing, or shorter than 20 characters) from `dshsa/github-app`. Set one under **Platform → GitHub App → Webhook secret (optional)** together with the private key, and paste the same value into the App |
| 202 but `{"ignored":"unrouted"}` | The repository isn't added as a cell. Add it under **Team setup → Repositories** |
| Delivery 202 but no acknowledgement | Look for `trigger not admitted` in `/dshsa/host`. Its `reason` says why: `not_a_member` (the sender isn't on the GitHub list in the Policy), `no_mention` (the comment doesn't mention `@<app-slug>`; an edited Issue body doesn't count, post a comment), `not_human` (a bot that isn't on the Policy's bot list). `at: intake` means the Source doesn't listen to that kind of message |
| **Link installations** says the sign-in failed, or GitHub reports a redirect URI mismatch | The App's **Redirect URI** must be exactly `<PanelUrl>/setup/github/callback`, and **Platform → GitHub App** must show **OAuth client: Set** with the App's Client ID. The sign-in is single use: start **Link installations** again |
| **Waiting for platform approval** | The reason is shown next to it. `not_own_account`: a user installation that isn't on the signed-in GitHub account. `not_org_admin`: the signed-in account isn't an admin of the organization. `membership_unavailable`: GitHub didn't confirm the org role, usually because the App lacks **Organization permissions → Members: Read-only** (grant it, and have the organization accept the new permission). A platform admin approves under **Platform → GitHub installations** |
| **Belongs to another team** (`other_tenant`) | Another team linked the installation. A platform admin can **Release** it under **Platform → GitHub installations**, then link again |
| **Unlink** or **Release** refused: `installation_in_use` (409) | Repositories of the team still use the installation; the message names them. **Disable** them under **Team setup → Repositories** first |
| Feishu console refuses to save long-connection mode | The Connector isn't connected yet: **Save bot** first and wait for **Connected** |
| The chat doesn't appear under **Chats** | The bot isn't in the chat, or nobody has @-mentioned it there yet. Health must be **Connected** |
| Feishu mention gets no reply | The chat isn't bound (`feishu.unrouted` in `/dshsa/host`), the bot isn't in the chat, or your `open_id` isn't on the Feishu list (`trigger not admitted` with `not_a_member`) |

## Appendix: CLI fallback

Every panel step has a `dshsa-admin` equivalent, for automation or when the panel isn't available. Run them with platform-admin AWS credentials. `admin` with no arguments prints the full usage. Replace the `<…>` values.

| Step | Command |
|---|---|
| First platform admin (step 2) | `admin user add-admin <email> [--temp-password <p>]` |
| GitHub App key (step 3) | `admin github app-set --app-id <APP_ID> --private-key-file <pem> [--webhook-secret <s>]` |
| OAuth client (step 3) | `admin github oauth-set --client-id <Iv…> --client-secret <secret>` |
| Team (step 3) | `admin tenant add <teamId> --name "<Team name>"`; `admin tenant disable\|enable <teamId>`; `admin tenant list` |
| Team admin or member (steps 3, 8) | `admin user add <email> --tenant <teamId> [--role member\|tadmin] [--temp-password <p>]`; `admin user remove <email> --tenant <teamId>`; `admin user list --tenant <teamId>` |
| Repository (step 5) | `admin cell add <teamId> --repo <owner>/<repo> --repo-id <REPO_ID> --installation-id <INSTALLATION_ID> [--default-branch main]`; `admin cell list [--tenant <teamId>]`; `admin cell pause\|disable\|enable <cellId>` |
| New installation id for a team's cells | `admin github-install register <teamId> <INSTALLATION_ID>` |
| Feishu / Lark bot (step 6) | `admin feishu set <teamId> --domain feishu\|lark --app-id <cli_APP_ID> --app-secret <secret> [--encrypt-key <k>]` |
| Chat binding (step 7) | `admin chat bind <teamId> <oc_CHAT_ID> <cellId> [--name "<chat name>"]`; `admin chat unbind <teamId> <oc_CHAT_ID>` |

Notes:

- `app-set` checks the App ID and key with GitHub (`GET /app`) and stores the App's real slug; `--slug` is optional, and a wrong one is refused. The slug is the last part of `github.com/apps/<slug>`, **not** the Client ID. It keeps the existing `webhookSecret` unless you pass `--webhook-secret`.
- `cell add` takes the ids from GitHub: the installation id is the number at the end of the installation page URL (`https://github.com/settings/installations/<id>`, or `…/organizations/<org>/settings/installations/<id>`), and the repository id is `gh api repos/<owner>/<repo> --jq .id`. The CLI trusts the operator: it doesn't link the installation to the team, so the panel's **Linked installations** doesn't list it.
- The chat id (`oc_…`) of an unbound chat is in the `feishu.unrouted` entries of `/dshsa/host` after someone @-mentions the bot there. With CloudWatch Logs Insights: `filter @message like /feishu.unrouted/`.
- Keep secrets out of shell history: read them with `read -rs`, which doesn't echo, and pass the variable. Press Enter after pasting:

  ```sh
  read -rs FEISHU_APP_SECRET && echo
  admin feishu set <teamId> --domain feishu --app-id <cli_APP_ID> --app-secret "$FEISHU_APP_SECRET"
  unset FEISHU_APP_SECRET
  read -rs GITHUB_CLIENT_SECRET && echo
  admin github oauth-set --client-id <Iv…> --client-secret "$GITHUB_CLIENT_SECRET"
  unset GITHUB_CLIENT_SECRET
  ```

- The Policy has no CLI. Without the panel's pickers, list a bound chat's members with their open_ids through the bot. This reads the App credentials from `dshsa/feishu/<teamId>` into a short-lived tenant token without printing either. On Lark use `https://open.larksuite.com` in both URLs. Each output line is an entry for `sources.feishu.allowed` in **Advanced (JSON)**:

  ```sh
  FEISHU_TOKEN="$(aws secretsmanager get-secret-value --secret-id dshsa/feishu/<teamId> --query SecretString --output text | jq '{app_id: .appId, app_secret: .appSecret}' | curl -s -X POST https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal -H 'content-type: application/json' -d @- | jq -r .tenant_access_token)"
  curl -s -H "authorization: Bearer $FEISHU_TOKEN" "https://open.feishu.cn/open-apis/im/v1/chats/<oc_CHAT_ID>/members?member_id_type=open_id&page_size=100" | jq -c '.data.items[] | {id: .member_id, name}'
  unset FEISHU_TOKEN
  ```

  GitHub entries are `{ "id": "<login>" }`; Feishu entries are `{ "id": "ou_…", "name": "…" }` with an optional `name`.
