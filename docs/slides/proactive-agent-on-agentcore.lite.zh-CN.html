背景

要解决的问题与架构要点

单 Session 的天花板

  • 主流 agent 以单个 Session 为工作单元
  • 单任务上限取决于模型能力
  • 多任务上限取决于人的注意力：一个人通常只能同时跟进 3–5 个活跃 session
  • 目标：让 agent 脱离单 Session 的限制，长期在线、跨平台保持上下文、并行推进多个任务

文章中的架构要点

  • Router + Worker 两层：Router 常驻，接收群聊、GitHub、邮件等消息并分派任务；Worker 持有独立上下文执行具体工作，完成后回报 Router 统一回复
  • 订阅：Worker 接手 PR 后，后续评论直接发给它
  • 主动触发 + 投机执行：规则过滤后由模型判断是否行动；后台静默修 bug，能修好才提交
  • 其他：异步 ReAct Loop、存算分离、外部 Watchdog

问题定义

两种 agent 的运行模型

差别不在模型能力，而在系统层：触发方式、状态、执行方式和输出纪律都不同。

维度被动响应的 chat agent主动感知的 agent（dsh-superagent 的做法）
触发用户发起一次提问持续接收 GitHub / 飞书事件流；被 @ 只是其中一种信号
判断默认每问必答程序闸门 + LLM 评估：先决定"要不要做"，大部分消息结论是不做
授权隐含在会话里名单、准入表、规则、接受模式；每个任务记录授权依据（Mandate）
状态一段对话历史持久化的 Thread / Ticket / 订阅 / Decision，模型上下文只是快照
执行同步生成回答异步派给隔离的 worker，每个任务独立会话和工作目录，可跨小时持续
输出每轮都输出只在需要人行动或结果可用时开口；进度不外发
可审计对话记录每次判断留 Decision；主动接受需引用证据；先观察模式再放开

表达

什么时候开口

确认一次、完成或卡住时回报、一次只问一个具体问题；其余时间保持安静。

ack · report · reply 闸门

设计原则（原型 docs/000-philosophy.md）：占用尽可能少的人的注意力，给出尽可能多的价值。 agent 只在被要求、或团队写下的规则允许时行动；只在有人需要行动或能用上结果时说话。
领域模型

九个核心概念

所有状态都落在这些对象上（原型存 SQLite）；模型看到的永远是它们的摘要。

Source 来源

GitHub、飞书等接入方式。负责把原始事件规范化，并给出回复通道。

Trigger 消息

规范化后的一条输入：评论、Issue、群消息、CI 结果。id 由来源确定性生成，重复投递自动去重。

Thread 对话

一段对话。GitHub 是一个 Issue/PR；飞书是一条顶层消息及其回复串。

Eval 判断

对一个 Thread 上一批待判消息的一次判断，有截止时间；同一 Thread 同时只有一个。

Decision 结论

Eval 的结果：accept / ignore / stop / reopen / unavailable，附理由，供审计。

Ticket 工作项

一件被接受的工作。id 由 Eval id 哈希得到，同一 Eval 重放不会开出第二个。

Mandate 授权

Ticket 的授权依据：强度、发起人、命中的规则、Policy 版本。恢复执行前会重新校验。

Assignment 执行

Ticket 与一个 worker 会话的绑定，记录状态和最近一次报告。

Subscription 订阅

"这个 Ticket 关注这个 Thread"。决定新消息直接送给 worker 还是进入 Eval。

一条消息的生命周期

判断 · 闸门

强度与接受模式：主动能力如何受控放开

闸门是确定性代码，先给每条消息定强度；主动（inferred）路径另受接受模式约束，默认只记录不执行。每个接收范围（飞书群、私聊、GitHub 新 Issue / PR / 评论 / CI）有一张准入表，按"发送者是否在名单""是否 @ 机器人"决定消息的强度；未 @ 的消息只在该范围接收全部消息时才可能进入。

explicit

明确请求

名单内的人 @ 或私聊机器人；名单内的人在已有 Ticket 的 Thread 上追问；准入表设为 explicit 的单元格。
任何模式下都生效。

inferred

推断候选

没人点名，但可能符合团队写下的规则：名单内的人未 @ 的讨论、名单上机器人的消息、名单外的人在已有 Ticket 上的追问。

不准入

直接记录

其他机器人、准入表 ignore 的消息、off 模式下的所有 inferred 情形。不调用模型。

接受模式inferred 候选的处理用途
off不产生候选只接明确请求
observe（默认）照常评估；评估为可接受时记为 ignore 并标注 would_accept，不开 Ticket上线初期审阅"本来会做什么"
auto评估为可接受且命中至少一条启用规则时，开 Ticket审阅满意后放开

规则、模式和各 Source 的 Policy 合成 Policy 版本。版本变化会作废进行中的 Eval 并重新排队，并通知受影响的在途 Ticket。

判断 · Eval（明确请求）

明确请求：路由而不是改写

判断者调用 orchestrator_route，对每条候选四选一。提示词 dispatch.md 的核心约束是：只做路由，不替人设计方案。

accept新工作

给出标题、worktree 名和一句确认回复。原话交给 worker，不附加配色方案、验收标准或检查清单；路由备注最多 30 词。

attach并入已有 Ticket

只有消息明确指向该 Ticket 才允许：引用了它的 PR/Issue、源消息或确认消息，或"刚才那个改动"且只有一个 Ticket 对得上。话题相近不算。

stop停止

有权限的人要求停止。worker 报告卡住不是 stop 的理由。

ignore普通讨论

写明理由，留下 Decision。

A@机器人 能加个暗色模式吗？
→ accept add-dark-mode，确认"好的，我来加暗色模式"
A@机器人 #42 那个按钮颜色再深一点
→ attach #42 属于某个 Ticket 的 PR，消息明确指向它
A@机器人 登录页也加个暗色模式
→ 新请求：accept 或 ignore，不能因为话题相近就 attach
A@机器人 暗色模式那个先别做了
→ stop 对应 Ticket
判断 · Eval（主动评估）

主动评估：没人点名时，凭什么接活

提示词 admission.md 要求：接受前必须确认三个事实，并对每条启用的规则逐一给出判断；拿不准就安静忽略。

①

针对本项目

讨论的是这个仓库，不是别家产品。

②

有实现意图

参与者想要一个具体改动被实现；短句附和一个具体提议也算。

③

方向已定

小的本地改动即可完成，没有留待产品或设计决定的部分。

结构化输出 orchestrator_eval_decide

  • direction：implementation_requested、target_basis（specified / existing-standard / undetermined）、requires_design_decision、evidence
  • rule_assessments：每条启用规则一项，matched + 理由
  • intent_evidence：三个事实的原文引用
  • decision：accept / ignore / unavailable（工具或读图失败）

规则（团队用自然语言编写，可增删）

  • copy：错别字、措辞、标点、现有翻译的修正
  • visual：局部间距、对齐、溢出、样式，需有明确目标或可恢复的现成标准
  • 范围上限：仓库内的小型内部改动；规则只能收窄，不能放大
  • Ticket 的 Mandate 记录命中的规则，worker 会收到规则原文

同样是群里的讨论，结论取决于意图和目标是否已经确定，而不是关键词。

A（转发一段别家产品的讨论）
B也许我们的 app 也可以像他们那样显示未读数

A（本项目截图）这个按钮文案有点怪
B就叫『保存』就行

ignore（安静）

"不一样""太高"都没有目标样式，target_basis = undetermined。不回复、不派活、不主动追问，等后续消息把方向说清楚。

其他约束：一条源消息最多一个 Ticket；规则冲突或范围模糊时 ignore；Thread 已有相关 Ticket 时 ignore 而不是重复接受；评估只读，不改文件、不发消息、不转交。

执行 · 订阅

订阅：让后续对话直接找到对的 worker

订阅存在 thread.subscriptions 中。它把"继续已有工作"与"判断新工作"分成两条路径，追问不必每次经过判断者。

何时建立订阅

  • accept：订阅触发消息所在的 Thread
  • attach：订阅被并入消息的 Thread
  • Ticket 开了 PR：订阅该 PR 的 Thread
  • worker 认为相关：仅作上下文的订阅

何时解除

  • worker 判定该 Thread 与本 Ticket 无关，并退回其中的消息
  • 有人在面板上退订

新消息到达时

  • 有订阅：作为 Input 直接投给 worker，不开 Eval，也不授予新权限
  • 已结束的 Ticket：有人发言即唤醒；机器人和 CI 不唤醒；被人 stop 的不再接收
  • 没有 Ticket 认领：人的消息和所有机器人消息进入 Eval
  • 仅上下文订阅：worker 能看到，但不唤醒、不认领

退回（handback）

worker 认为追问超出本 Ticket 范围，或属于别的 Ticket，就退回并写明理由。消息带着 handed_back 重新成为候选，不能再并回原 Ticket。

执行与表达

worker 与回报纪律

判断者不读代码、不调查技术问题；worker 回到源头读原文，自己判断需求、实现和验证。

worker 的工具（与控制面的全部接口）

工具作用
ack确认已接手某条消息
reportprogress / waiting / ready / blocked / failed / dropped，可带一个具体问题、PR 号
handback退回超出范围的消息
thread.follow为上下文关注另一个 Thread
thread.unrelated声明某个 Thread 与本 Ticket 无关

每个 Ticket 一个独立会话和工作目录；按影响范围停止：本地改动做到可审阅的结果，需要设计决定的就停下来提问。

什么时候对外说话

  • 接受时确认一次，说明要做什么
  • ready、blocked、failed、dropped，或报告里带问题时才组织回复
  • 回复可以选择不发（send=false）
  • 回到 Ticket 最初来源的对话；飞书来源的结果不以 GitHub 评论代替
  • PR 合并 / 关闭通知由程序发一次，不重复宣布

被忽略的消息

每次 ignore 都留 Decision。AWS 实现另有 decision ignored 日志、面板"最近被忽略"列表，以及明确请求被忽略时的一次提示回复（可配置）。

原型 · router

只放路由需要的信息，状态在数据库，细节用指针

原型用一个长期存在的 DeepSeek Harness 会话（main Session，即 router）承担判断与回复，需要控制这条不断变长的对话。

卡片而非原文

推给 router 的是截断的候选卡片：消息、Thread 上的 Ticket（最多 8 个）、已送达、被引用的 Ticket、退回理由。细节用 orchestrator_read 按资源名读：ticket/<id>、thread/<key>……文本页 4–8k 字符，列表分页。

两种推送

relay（唤醒）：候选卡片、follow_up、worker 报告（摘要 ≤600 字符）。
notice（只追加）：Ticket 结束、设置变更等。同名 notice 未送达时被替换；router 自己做的操作不回送 notice。

提示词每次重拼

规则与 Policy 不依赖对话历史，每次调用前从当前设置生成；Policy 段放最后，修改立即生效且不打乱前缀。router 不读仓库的 AGENTS.md。

主动评估的有界窗口

orchestrator_eval 给出：Trigger ≤4,000 字符、相关 Ticket ≤8、Thread 前 5 条 + Trigger 前后各 5 条，其余为 50 字符 stub，可按 id 展开或读图。

压缩交给 Harness

应用层不做压缩；提示词要求压缩后重新查看 Ticket 摘要。程序兜底：accept 按 Eval 幂等、relay/notice 按 request id 去重。

不让它等待

noWait 守卫拒绝 sleep、>30 秒的 shell timeout、>5 秒的 job wait。新候选和报告会自动推送，停下来等只会积压。

结果：router 的上下文里基本只有"谁、什么事、交给了谁、结果如何"。
架构

总体架构

控制面 · cell

cell 的运行方式

cell 不是独立进程：一个 Fargate task 是一个 Node 进程，进程内承载多个 cell 对象。

Fargate task（dshsa-host） └─ Node 进程：HostProcess ├─ cell A │ ├─ Engine + Policy 闸门 + Effects 队列 │ ├─ SQLite /data/cells/A/orchestrator.sqlite │ ├─ Assessor · Replier · Executor · Outbox │ ├─ SQS 消费循环（cell A 的 FIFO 队列） │ └─ 子进程 litestream replicate → s3://…/cells/A/ ├─ cell B …（默认最多 20 个） ├─ 飞书 Connector（默认最多 5 个） └─ 内部 HTTP :8080

租约与迁移

  • 租约 cell#<cellId>：TTL 30 秒，每 10 秒续约，条件写 owner = 我 AND fence = f
  • 续约失败或临近过期：先停消费、停写、关库，再放手
  • 接手方只接过期租约，fence + 1，先 litestream restore 再打开数据库

为什么每个 cell 一个 SQLite

  • 沿用原型存储模型，Engine 无需改动
  • cell 之间故障隔离，迁移粒度清晰
  • Fargate 本地盘不持久，S3 上的 Litestream 副本才是持久那一份
控制面 · 判断

无状态 Assessor / Replier

同一套提示词和工具 schema，换成"一次调用一个决定"。模型必须调用与原型同名的工具，结果交给同一个 Engine 执行。

Assessor 每次调用的输入

部分内容
system 前缀原型 router 的全部提示词段落 + 无状态说明；走 prompt cache
system 尾部Policy 段（启用规则、接受模式），放在 cache 点之后
卡片本批 Trigger、Thread 上的 Ticket（含最近报告摘要 ≤300 字符）、送达与退回情况
Thread 上下文仅 inferred：从 GitHub / 飞书现读最近 20 条

explicit 候选调用 orchestrator_route；inferred 调用 orchestrator_eval_decide。

运行约束

  • 截止时间 = Eval 超时（默认 120 秒）；并发上限 4
  • 失败记为 unavailable，由 Engine 按原型规则重排重试
  • Replier：仅 ready / blocked / failed / dropped 或带问题的报告触发，调用 orchestrator_reply，可选择不发
  • 模型按 cell 在面板配置

上下文管理的变化

  • 没有历史 → 不需要压缩，也没有压缩后遗忘
  • 不能按需再读 → 卡片要一次给够；提示词要求不编造 id 或引文
  • 一个候选失败只影响一个 Eval，不会阻塞其他候选
  • notice 没有接收者，只记录给面板
数据面 · worker

worker：每个 Ticket 一个 AgentCore Runtime 会话

cell 通过 InvokeAgentRuntime 下发 start / deliver / stop / status；worker 异步运行，通过 worker-api 回传事件。

会话与身份

  • runtimeSessionId 由 cellId + ticketId 派生，同一 Ticket 始终落在同一会话
  • gateway 以 root 运行，持有 token；agent 以 uid 1000 运行，经本地代理访问控制面
  • 两种 worker：Claude Agent SDK、Codex（Bedrock），按 cell 选择

存储布局

  • 本地盘：git 工作区（实测 S3 Files 上 git 慢 17–384 倍）
  • S3 Files AP（每 Ticket 一个）：对话记录 JSONL、inbox、state、repo.bundle
  • 每轮结束做 checkpoint：未提交改动写入 refs/dshsa/wip，增量打包到 bundle

换 microVM 后续做

  • 同一会话 id 上的下一次调用会拿到新 microVM，挂载同一个 AP
  • 从 GitHub 部分克隆，再从 bundle 恢复分支和未提交改动
  • Agent SDK 用同一份对话记录 resume
  • 最多丢失上次 checkpoint 之后的未提交编辑

worker-api（私有 API GW）：/v1/events 回传 ack / report / handback / thread.follow 等事件，进入 cell 队列；/v1/read 只读本仓库与已绑定飞书群；/v1/credentials/github 签发 ≤1 小时的仓库 installation token；/v1/token/refresh 仅在 Assignment 运行中续签。

安全

安全模型：worker 按不可信处理

层机制
Runtime 入口AgentCore 入站认证为 IAM；只有 host task 角色有 InvokeAgentRuntime；无人拥有 InvokeAgentRuntimeCommand
Ticket 身份KMS 非对称密钥签发的 ES256 ticket token，含 tenant / cell / ticket / assignment / session，有效期 ≤2 小时；只有 cell 签发
存储每 Ticket 一个 S3 Files access point；挂载凭证的 session policy 限定该 AP；执行角色本身没有 S3 / S3 Files 权限
VM 内gateway root、agent uid 1000 + NoNewPrivs；一个 VM 绑定第一个 token 的 ticketKey
worker 出口worker-api 为私有 AWS_IAM API（runtime 角色 + VPC endpoint 条件）且要求 ticket token；访问范围取自 token，不取自请求
面板Cognito JWT，按 cognito:groups 校验 tenant 归属后转发到内部 HTTP
入口GitHub webhook HMAC 校验（密钥在 Secrets Manager）+ API GW 限流；飞书走长连接，不需要公网入口

提示词层：所有消息、引用和仓库文件都按不可信数据处理；转发的指令不构成授权；Thread 上下文不能覆盖名单、规则和明确的 stop。

可靠性

可靠性：确定性 id、持久化副作用、幂等

Effects 队列（outbox 模式）

Engine 在同一个 SQLite 事务里写状态和"要做的外部动作"，提交后由后台按行执行，成功才删除。

kind动作
assessment一次 Bedrock 判断
compose为报告写回复
launch / delivery / stop启动、投递、停止 worker
reply发 GitHub / 飞书消息

按 (kind, key) 合并；指数退避重试；按 kind 限并发；暂停时原地等待；随 cell 的 SQLite 一起迁移。

确定性 id

Trigger id 由来源 id 哈希；Eval id 由 Thread、Policy 版本、时间和批内 Trigger 哈希；Ticket id = hash('ticket', evalId)。webhook、补拉、重放产生的重复在入库时合并。

多层去重

SQS FIFO 按 envelope id 去重；worker 事件按 uuid 去重（跨重试和重启不变）；worker 端 deliver 按 input id 去重；start 按 assignmentId 幂等。

超时与失败

Eval 超时重新排队，连续两次重试后第三次超时记 unavailable；面板只对 24 小时内、仍是最新且未处理的 unavailable 提示人工。

取舍

得到的与失去的

得到的

  • 可复现：每次判断的输入是一张固定卡片，便于审计和回归测试
  • 无上下文膨胀：没有压缩带来的遗忘与重复派活
  • 横向扩展：cell 之间互不影响，host 可多实例
  • 故障隔离：一个候选失败不拖住其他候选
  • 成本可控：system 前缀走 prompt cache，Policy 段在 cache 点之后
  • 执行隔离：worker 在独立 microVM，按 Ticket 限定存储与凭证

失去的 / 已知限制

  • 按需查资料：卡片外的 Ticket、Decision、Thread 细节仍读不到。暂不加只读工具循环，因为：每查一轮多一次模型调用，延迟和 token 叠加；模型主动读更多他人原文，提示注入面变大；判断输入不再只是一张卡片，复现和审计变弱。先从 eval 日志找出因信息不足而判错的实例，再决定是否做
  • 对话式管理：改设置、发 note、查 worker 状态在面板完成
小结

要点

主动 ≠ 每条都回。主动 agent 的大部分判断结论是"不做"；系统的价值在于判断是否准确，以及判断的依据是否可审计。

确定性代码管边界，LLM 管语义判断。名单、准入、订阅、去重、重试都由代码完成；模型只做 Eval、执行和回复措辞，并以结构化工具输出。

判断与执行分离。判断者只看摘要卡片，不读代码；worker 回到原始消息自行理解需求，范围外的退回。

AWS 实现保留内核，替换运行时。Engine、提示词、工具 schema 原样复用；cell 单写者 + Litestream、无状态 Bedrock 判断、每 Ticket 一个 AgentCore Runtime 会话与 S3 Files AP。
